 Proyecto 1:   Diseño e implementación de un sistema de archivos distribuido con alta
disponibilidad, rendimiento y seguridad (DFSha)
 Objetivo General:
 Diseñar e implementar un   DFS   que permita almacenar y acceder a archivos grandes de forma
distribuida en múltiples nodos, considerando alta disponibilidad, rendimiento, transparencia y
seguridad. Este DFS debe permitir que un cliente cargue y recupere archivos (tanto la escritura
como la lectura deben ser distribuidas entre varios nodos).
 Descripción del servicio
 Típicamente estos sistemas pueden ser modelados e implementados con al menos (generalmente
existen más) estas componentes:
 Cliente DFSha: Programa que es usuario del sistema dfsha y que con una abstracción de sistema
de archivos jerárquico tipo Linux, puede realizar operaciones de:
 ●   RF1: Gestión del sistema de archivos: ls, cd, mkdir, rmdir, rm, etc.
 ●   RF2: Transferencia de archivos: send() y receive()
 ●   RF3: Acceso a archivos: open(), close(), read(), write(), lock(), etc. Realmente las
operaciones send() y recv() pueden ser implementadas con estas primitivas, pero hay
diferencias fundamentales entre ambos tipos de servicios de archivos: transferencia y
acceso.
 Normalmente, el programa Cliente no es parte del servicio, y desde ese punto de vista es
implementado   como   una   arquitectura   cliente/servidor,   sin   embargo   a   continuación
describiremos opciones de arquitectura para el lado del Servidor (servicio).
 Servicio DFSha: El servicio puede ser diseñado e implementado siguiendo varias arquitecturas
de sistemas de archivos distribuidos (dfs), igualmente e independiente de la arquitectura debe
cumplir entre otros los siguientes requisitos:
 ●   RNF1: Escalabilidad en número de usuarios, número de archivos, tamaño de archivos,
etc.

 El servicio DFSha puede ser implementado utilizando una combinación de arquitecturas:
 Opción 1: C/S, en el cual el S es implementado por mecanismos de Composición y Distribución
del servicio (S2S). En este acercamiento se considera un sistema autónomo, es decir, el servicio
es diseñado e implementado por una misma organización y define mecanismo abiertos para
acceso al servicio entre C y S, pero mantiene la autonomía S-S. La implementación del servicio
S corre dentro de una red privada real o virtual.
 Opción 2: P2P, en el cual el servicio es implementado por un conjunto de SuperPeer, que
pertenecen a organizaciones diferentes (sistema federado e integración de sistemas autónomos).
Estos servicios así corren en una red superpuesta sobre Internet configurada a través de una red
privada virtual.
 Marco teórico:
 Un sistema de archivos distribuidos, permite compartir y acceder de forma concurrente un
conjunto de archivos que se encuentran almacenados en diferentes nodos. Uno de los sistemas
más maduros, vigente y antiguo de estos sistemas es el NFS (Network File System) desarrollado
en su momento por Sun Microsystems y que hoy en día es ampliamente usado en sistemas
Linux. Hay otros sistemas de archivos distribuidos como AFS (Andrew File System) y SMB
(Server Message Block) conocido como CIFS.

En general hay dos acercamientos para el diseño e implementación de un DFS: 1) basado en
bloques y basado en objetos.
 Los DFS basados en bloques generalmente garantizan 2 aspectos: 1) la unidad de escritura y
lectura es a nivel de bloque, y los bloques pueden ser distribuidos en diferentes nodos, la idea es
que los bloques de un archivo estén distribuidos en un conjunto de nodos. 2) el sistema operativo
cliente de un DFS garantiza transparencia en el sentido de que la API ofrecida desde el SO es
igual para acceder archivos locales que remotos, porque el DFS se integra con el sistema de
gestión de archivos del sistema operativo (ej: NFS, AFS, SMB, etc).
 Los DFS basados en objetos (object storage, ej: AWS S3), los dos aspectos anteriores se manejan
así: 1) la unidad de distribución es a nivel de archivo y no de bloque, es decir, y se garantiza que
se lee o escribe un archivo como un todo y no a nivel de bloque. No está diseñado como un
sistema de acceso aleatorio al archivo sino secuencial. No soporta la operación de actualización
parcial del archivo, sino que se debe reemplazar todo el archivo. Son sistemas distribuidos de
archivos   principalmente   diseñados   para   un   enfoque   WORM   (Read-Once-Read-Many).
Típicamente estos DFS soportan altos niveles de escalabilidad, redundancia y rendimiento. Si
bien desde el cliente tiene una visión de archivo completo, en el sistema de backend podría tener
(y normalmente lo hay) un mecanismo de particionamiento del archivo por bloques u otro
criterio para mejorar la escalabilidad, tolerancia a fallos y rendimiento. 2) el sistema operativo
local del cliente NO integra directamente la gestión de este DFS y en vez de ello se cuenta con
un SDK o API para las diferentes primitivas de la gestión de archivos y normalmente tienen su
propio CLI.

Desarrollo del proyecto
 1.   Definición del Servicio
 Cada grupo de estudiantes debe realizar la definición formal de este proyecto utilizando La
Descripción del Servicio del enunciado, que permita hacer más explícito el entendimiento del
mismo y los requerimientos funcionales y no funcionales que cada grupo tendrá.
 A cada grupo de trabajo, se le asignará la opción 1 o la opción 2 para la implementación del
servicio.
 Ejemplo:
 En este proyecto se construirá como   DFS por bloques,   siguiendo una arquitectura tipo HDFS:
 ●   Un   NameNode   central que mantiene la   tabla de metadatos   (ubicación de bloques por
archivo).
 ●   Múltiples   DataNodes   que almacenan los bloques.
 ●   Clientes que interactúan con el DFS a través de una   CLI (interfaz de línea de
comandos)   o API.
 Operaciones básicas:
 ●   put <archivo> : dividir un archivo en bloques y distribuirlos en DataNodes
 ●   get <archivo> : recuperar un archivo reconstruyéndose a partir de los bloques
 ●   ls, rm, mkdir, rmdir : comandos básicos de gestión del file system
 ●   Cada cliente gestiona   solo sus propios archivos   mediante una autenticación básica
(user/pass).
 ●   Además debe contar con APIs – operaciones básica de lectura / escritura de archivos
(bloques) desde clientes.
 2.   Arquitectura del Sistema
 ●   Definir el tipo de arquitectura de acuerdo a la opción asignada por el profesor:   C/S,
P2P o alguna variante o integración de las mismas
 Ejemplo:
 ●   Tipo de arquitectura:   Maestro – Trabajador (Master–Workers) o P2P no estructurado
con servidor replicado central de metadatos.
 3. Comunicaciones de red:   el proyecto debe correr o ejecutar sobre Internet (p. ej., nodos
comunicándose por REST, gRPC o sockets TCP).
